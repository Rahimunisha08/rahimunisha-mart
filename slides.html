Problem Statement & Project Objectives

Industry challenges & academic requirements addressed
Slide 2 / 9
⚠️ Current Industry Pitfalls
  • Concurrency & Overselling: Lack of atomic transactional locking permits double-spending and out-of-stock checkouts.
  • SQL Injection Risks: Concatenated dynamic SQL strings in legacy JDBC expose sensitive data.
  • Connection Overhead: Unmanaged connections cause high latency, memory leaks, and socket exhaustion.
  • Support Latency: Static stores lack immediate automated answers for shipping and returns.
🎯 Project Solutions & Goals
  • Strict 3-Tier Layered Architecture: Presentation, Service, and DAO segregation without tight coupling.
  • Atomic ACID Checkouts: Single-transaction commit/rollback blocks to preserve stock boundaries.
  • 100% PreparedStatements: Complete elimination of SQL injection vulnerabilities.
  • HikariCP Connection Pool: Sub-10ms query execution times and zero connection leakage.
  • Dual-Mode AI Assistant: Real-time Gemini LLM assistance with offline fallback rules.
🗣️ Viva Note: Existing academic projects often suffer from race conditions and SQL injection. Our goal was to build a resilient, strictly layered system implementing full ACID transactions, pooled connections, and conversational customer support.

System Architecture & Design Patterns

Layered enterprise decoupling & design pattern compliance
Slide 3 / 9
🖥️ Presentation Layer
  • HttpServlets: Controller dispatches (Auth, Cart, Order, Product, Seller, Admin, Chat).
  • Filters: AuthFilter for RBAC and EncodingFilter for UTF-8.
  • Views: JSP 2.3 + JSTL 1.2 with automated XSS escaping.
⚙️ Business Logic Layer
  • Services: CartService, OrderService, ProductService, UserService.
  • Validation: Centralized ValidationUtil.
  • Exception Handling: Custom checked/runtime domain exceptions.
🗄️ Data Access Layer
  • DAO Interfaces: UserDAO, ProductDAO, OrderDAO, etc.
  • JDBC Implementations: Pure PreparedStatement execution.
  • HikariCP: High-performance connection lifecycle pooling.
💡 Key Patterns: Front Controller (Routing) | Data Access Object (Persistence decoupling) | Singleton (DatabaseUtil) | Strategy & Factory Patterns (Pluggable AI Chat Subsystem).
🗣️ Viva Note: We enforced strict physical separation of concerns. Controllers only invoke Services, and Services communicate through DAO interfaces, ensuring modular testability and zero architectural pollution.

Database Design & Security Compliance

Normalized relational schema & enterprise defensive architecture
Slide 7 / 9
🗃️ 7 Normalized Database Tables
  • users: Credential hashes, contact details, role type.
  • products: Foreign key to sellers, status, inventory count.
  • orders & order_items: Master-detail transactional records with prices frozen at purchase time.
  • cart_items & wishlist_items: User-specific product bookmarks.
  • reviews: Verified buyer ratings linked to product items.
🛡️ Security Checklist Compliance
  • SQL Injection: 100% PreparedStatements; zero string concatenation.
  • Zero Plaintext: BCrypt salted password hashing (work factor 10).
  • Session Rotation: req.changeSessionId() prevents session fixation.
  • Role-Based Access: AuthFilter guards restricted paths.
  • Stack Trace Masking: Custom HTTP 403, 404, 500 error views.
🗣️ Viva Note: The database design follows 3rd Normal Form. Prices in order_items are explicitly snapshotted so future catalog price changes never alter historical accounting data. All OWASP Top 10 web vulnerabilities are mitigated.
